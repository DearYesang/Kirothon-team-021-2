# Requirements Document

## Introduction

집중비서는 여러 메일함(지메일·네이버메일·네이버웍스·아웃룩)을 쓰는 대학생과 사회초년생이 받은 메일에 답장할 때
드는 작은 결정(지금 할까, 무슨 내용이지, 어떤 말투, 어떤 문장, 일정 되나, 어디 적지)을 줄여 집중력을 아끼게 하는 웹 앱이다.
사용자는 메일을 붙여 넣고 "어떻게 답할지" 하나만 고른다. 메일 원문은 브라우저 밖으로 나가지 않는다.

## Requirements

### Requirement 1: 메일 이해 (요약·내가 할 일)

**User Story:** 학생으로서, 긴 메일을 끝까지 정독하지 않고도 상대가 나에게 원하는 것을 바로 알고 싶다. 그래야 읽는 데 집중력을 쓰지 않는다.

#### Acceptance Criteria

1. WHEN 사용자가 메일 본문을 붙여 넣고 분석을 누르면 THEN 시스템은 3문장 이하의 요약을 보여 주어야 한다(SHALL).
2. WHEN 본문에 요청 표현(~주세요, 부탁드립니다, 알려줘 등)이 있으면 THEN 시스템은 '내가 할 일'로 최대 3개를 뽑아야 한다(SHALL).
3. WHEN 본문 앞에 보낸사람/받는사람/제목(From/To/Subject) 줄이 있으면 THEN 시스템은 이를 본문과 분리해 보낸 사람 이름·직함·주소와 제목으로 해석해야 한다(SHALL).
4. IF 입력이 비어 있으면 THEN 시스템은 분석하지 않고 안내 문구를 보여 주어야 한다(SHALL).

### Requirement 2: 집중력 비용과 처리 시점

**User Story:** 바쁜 사용자로서, 메일마다 지금 처리할지 나중에 몰아서 할지 알려 주면 좋겠다. 그래야 하던 일이 메일 때문에 끊기지 않는다.

#### Acceptance Criteria

1. WHEN 메일을 분석하면 THEN 시스템은 집중력 비용을 가벼움·보통·무거움 중 하나와 0~100 점수로 보여 주어야 한다(SHALL).
2. WHEN 비용을 계산하면 THEN 시스템은 길이, 요청 개수, 검토·수정·보고서·첨부 같은 결정 단어, 날짜 개수를 반영하고 그 이유를 짧은 문장으로 보여 주어야 한다(SHALL).
3. WHEN 비용이 가벼움이면 THEN 처리 시점은 '지금', 보통이면 '몰아서', 무거움이면 '집중 시간에'여야 한다(SHALL).
4. IF 마감이 오늘이나 내일이면 THEN 비용과 상관없이 처리 시점은 '지금'이고 이유에 마감을 적어야 한다(SHALL).

### Requirement 3: 관계 기반 톤앤매너 추천

**User Story:** 교수님께 메일을 쓰는 학생으로서, 어떤 말투가 맞는지와 그 이유를 알고 싶다. 그래야 "실례 아닐까" 걱정하는 데 마음을 쓰지 않는다.

#### Acceptance Criteria

1. WHEN 메일을 분석하면 THEN 시스템은 상대를 교수님·직장 상사·채용 담당자·고객·선배·동료·친구·알 수 없음 중 하나로 판별해야 한다(SHALL).
2. WHEN 관계가 정해지면 THEN 시스템은 `.kiro/steering/tone-guide.md`에 따라 말투(격식체·해요체·반말), 지킬 규칙 2~3개, 한 문장 이유를 보여 주어야 한다(SHALL).
3. IF 관계 단서가 없으면 THEN 시스템은 해요체를 추천해야 한다(SHALL).

### Requirement 4: 답장 자동완성

**User Story:** 답장을 써야 하는 사용자로서, 수락·거절 같은 의도만 고르면 상대에게 맞는 문장이 완성되면 좋겠다. 핵심만 대충 적어도 정중한 메일이 되면 더 좋다.

#### Acceptance Criteria

1. WHEN 분석이 끝나면 THEN 시스템은 의도 5개(수락·다른 날짜 요청·정중히 거절·질문하기·확인했어요)를 메일에 가장 맞는 순서로 보여 주어야 한다(SHALL).
2. WHEN 사용자가 의도를 고르면 THEN 시스템은 정중·표준·간결 세 가지 초안(제목 포함)을 만들어야 한다(SHALL).
3. WHEN 사용자가 '핵심만 대충 쓰기'에 메모(예: "목 안됨 금 3시 가능")를 넣으면 THEN 시스템은 메모를 추천 말투의 문장으로 다듬어 초안 본문에 넣어야 한다(SHALL).
4. WHEN 상대가 교수님이면 THEN 초안은 소속·이름으로 시작하고 '올림'으로 맺어야 한다(SHALL).
5. WHEN 사용자가 복사를 누르면 THEN 시스템은 초안을 클립보드에 복사하고 '복사됨'을 보여 주어야 한다(SHALL).

### Requirement 5: 일정 조언과 캘린더

**User Story:** 면담·면접 일정을 자주 잡는 학생으로서, 메일 속 날짜와 내 일정을 비교해 가능한 시간을 제안받고 바로 캘린더에 넣고 싶다. 그래야 일정이 머릿속에 남지 않는다.

#### Acceptance Criteria

1. WHEN 본문에 날짜·시간 표현(11월 16일, 11/16, 내일, 다음 주 월요일, 수요일 오후 3시 등)이 있으면 THEN 시스템은 날짜(YYYY-MM-DD)·시간·종류(마감·약속·날짜)를 뽑아야 한다(SHALL).
2. WHEN '다음 주 중'처럼 날짜를 정해 달라는 요청이 있으면 THEN 시스템은 내 일정 메모의 바쁜 시간을 피해 서로 다른 날의 후보 3개를 제안해야 한다(SHALL).
3. WHEN 사용자가 내 일정 메모(예: "화·목 오후 수업")를 입력하면 THEN 시스템은 이를 저장하고 다음 분석에도 써야 한다(SHALL).
4. WHEN 사용자가 캘린더 추가를 누르면 THEN 시스템은 구글 캘린더 일정 만들기 링크를 새 탭으로 열고, .ics 저장을 누르면 RFC 5545 형식 파일을 내려받게 해야 한다(SHALL).

### Requirement 6: 개인정보와 공개 데모

**User Story:** 실제 메일을 다루는 사용자로서, 내 메일 내용이 어디에도 전송되지 않기를 원한다. 심사위원은 설치나 키 없이 데모를 열 수 있어야 한다.

#### Acceptance Criteria

1. THE 시스템은 메일 원문을 네트워크로 보내지 않아야 한다(SHALL). (외부 스크립트·폰트·API 호출 없음)
2. THE 시스템은 API 키 없이 GitHub Pages에서 그대로 동작해야 한다(SHALL).
3. WHEN 화면에 사용자·메일 텍스트를 넣을 때 THEN 시스템은 HTML로 해석하지 않아야 한다(SHALL). (textContent 사용)
4. THE 레포에는 API 키·토큰·.env가 없어야 하며, 비밀정보 검사 스크립트로 확인할 수 있어야 한다(SHALL).
